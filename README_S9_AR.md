# حسابات مستشفى رمسيس — S9 | فتح وردية حسب تاريخ التشغيل

**للاختبار والتطوير فقط — ممنوع استخدامه في التحصيل أو القيود الفعلية بالمستشفى.** لم يتم نشر هذا الإصدار، ولم تُستخدم بيانات مرضى أو موظفين حقيقيين.

## المشكلة التي تم إصلاحها

عند تجهيز جدول جديد لنقطة كاشير يبدأ سريانه في يوم لاحق، كانت شاشة «فتح وردية» في قسم الورديات وشاشة الحالات والفواتير تعرض آخر جدول محفوظ، حتى عند اختيار يوم سابق له. قد يختار الموظف اسمًا/كودًا غير ساري، فيرفضه الخادم عند التسجيل؛ كما تتسبب الحيرة في وقت تسليم العهدة.

## التغيير

أضفنا استعلامًا للقراءة فقط `GET /api/shifts/open-options` يأخذ رقم الخزنة وتاريخ يوم العمل. يحدد الخادم نقطة الكاشير والجدول المعتمد الساري وقتها وأيام العمل المسموحة وحقوق الموظف في الوردية والخزنة الحساسة. تعمل شاشتَا فتح الوردية على النتيجة نفسها، وتعيدان تحميل الاختيارات مع تغيير التاريخ أو الخزنة؛ وتُعطلان زر التأكيد أثناء التحميل أو عند عدم وجود فترة متاحة.

يمكن **معاينة** جدول يبدأ في المستقبل، لكن لا يمكن فتح الوردية المستقبلية. عند التأكيد، يعيد المسار المالي الأصلي `/api/shifts/open` فحص الصلاحيات والتاريخ والتعاقب الزمني والوردية المفتوحة والفترة المحاسبية؛ أي أن الاستعلام الجديد ليس وسيلة لتجاوز المراجعة. استمرت شاشة الورديات التاريخية في استخدام الاسم المعتمد في تاريخ كل وردية كما في S8.

**لم يتغير:** مبلغ، قيد أستاذ، حجز مريض، قيمة مستهلك، صلاحية فعلية، جدول SQL، سجل تاريخي أو سياسة إغلاق فترة. لم نضف صفحات جديدة.

## التجربة وإعادة التحقق

من مجلد السورس، في بيئة تطوير تحتوي على Python وFastAPI والمكتبات المستخدمة وChromium:

```bash
python tests/test_s9_shift_open_options.py
python scripts/qa_s9_http.py
python tests/browser_s9_shift_open_options_offline.py
python tests/test_s8_historical_shift_identity.py
python tests/test_s2_cashier_24h_acceptance.py
S4_REAL_HTTP=1 python tests/test_s4_integrated_day.py
python scripts/ci_smoke.py
python scripts/qa_g2t_full.py
```

اختبارات S9 على قاعدة SQLite مؤقتة بموظفين وهميين. اتصال HTTP في الاختبار المحلي عبر Uvicorn هو HTTP على `127.0.0.1` فقط، وليس HTTPS ولا شبكة المستشفى. Chromium يستخدم بيانات API تجريبية مبرمجة داخل الاختبار ولا يُثبت سلوك أجهزة المستشفى.

توجد نتائج الاختبارات التفصيلية وملخصاتها في `QA_S9_*` وتقرير التسليم، ويُذكر الاختبار الذي لم يُنفذ بسبب غياب V8.0 باعتباره **BLOCKED** وليس نجاحًا.

## موانع التشغيل الفعلي

1. النسخة الأصلية المعتمدة من V8.0 للتأكد من الترحيل والأرصدة الافتتاحية.
2. استعادة نسخة مشفرة على جهاز آخر مستقل، مع محضر وتجربة موثقة من فريق IT.
3. اختبار الكاشير على شبكة المستشفى الفعلية: HTTPS، الأجهزة، الطابعة، المرفقات وسياسات تسليم العهدة.
4. اعتماد الإدارة المالية والطب وإدارة النظام، وقرار مكتوب بخصوص استثناءات الحساب 2200 للموردين قبل إقفال الفترة.
