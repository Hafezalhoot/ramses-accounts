# نظام حسابات رمسيس — S5 إصلاح عيب التزامن في HTTP وSQLite

**الإصدار:** `V8.1E-G3N-S5` / `TEST_ONLY` / `NO-GO PRODUCTION`
**القاعدة:** S4 commit `60bddc126c7fcb524aadcd59cf149ee9f317387b`
**فرع العمل:** `stabilization/s5-contention`

## السبب المثبت قبل الإصلاح

أثناء تشغيل FastAPI تحت التزامن، إنشاء الاتصال في dependency مثل `app.db()` لا يضمن أن تنفيذ endpoint وإغلاق dependency يحدثان على نفس خيط التنفيذ. كان `bootstrap.connect()` ينشئ اتصال SQLite بخيار `check_same_thread=True` الافتراضي. اختبار HTTP على أصل S4 أعاد إنتاج `sqlite3.ProgrammingError: SQLite objects created in a thread can only be used in that same thread` في `billing.assign_point`، ومعه 65 رد 500 و17 خطأ اتصال من أصل 96 طلبًا متزامنًا (14 رد 200). ظهرت 15 حركة في audit مقابل 14 رد نجاح: رد خطأ قد يصل حتى لو حدث تغيير، مما يستدعي الحذر من إعادة إرسال العمليات التي لا تستخدم request_id.

بعد السماح باستخدام اتصال الطلب عبر الخيوط المختلفة (`check_same_thread=False`) اختفت أخطاء thread affinity في اختباراتنا. تحت ضغط أشد (48 عاملًا و384 عملية) ظهر `sqlite3.OperationalError: database is locked` بعد نحو 10 ثوان بسبب `PRAGMA busy_timeout=10000`، الذي كان يلغي مهلة `sqlite3.connect(timeout=30)` الأصلية.

## التصحيح الأدنى

- `bootstrap.connect()` يفتح كل اتصال جديد بـ `check_same_thread=False`، مع بقاء دورة حياته مقيدة بالطلب في `app.db()` وعدم مشاركة اتصال واحد بين طلبات مستقلة.
- حذف سطر `PRAGMA busy_timeout=10000` الزائد؛ مهلة `timeout=30` الموحدة في sqlite3 تضبط `busy_timeout` تلقائيًا على 30000 ملي ثانية.
- **لا تغيير** في منطق القيود المزدوجة أو نظام التفويض أو جداول قاعدة البيانات أو طريقة الترحيل أو شاشة المستخدم.
- إضافة `tests/test_s5_cashier_http_contention.py`: HTTP فعلي على Uvicorn وSQLite مؤقتة، 12 حسابًا صناعيًا، جلسة مستقلة لكل عامل، مطابقة طلبات النجاح مع audit، فحوص سلامة وفروع 403، وحفظ traceback في حالة الفشل.

## لماذا لا تزال المستشفى غير جاهزة للإنتاج؟

اختبار S5 إثبات فني على قاعدة صناعية وخادم HTTP محلي، وليس قياسًا لحمل المستشفى ولا وثيقة قبول مالي. لم تُختبر HTTPS، الأجهزة الفعلية، الشبكة الداخلية، الطابعات، استعادة مشفرة على جهاز مستقل، أو ترحيل أرشيف V8.0 الأصلي. التطبيق لا يقوم بتحويلات مصرفية في هذه الاختبارات. لا تغير ضوابط البيئة الحقيقية أو مستخدميها أو بيانات مرضاها بناءً على هذه النتائج وحدها.
