**الأساس:** S6 commit `8feca982026c5466aafd6b58a2fc8101d5577532`.

## ماذا أصبح موجودًا فعلًا؟

أداة `scripts/recovery_drill.py` مستقلة عن واجهة التشغيل، وتعمل محليًا وبلا شبكة على نسخة `.rbe` مشفرة من قاعدة المستشفى. تتطلب بصمة SHA-256 للأرشيف مأخوذة من جهاز النسخ الأصلي بشكل مستقل؛ ترفض اختلافها **قبل فك التشفير**، وتنقل الأرشيف إلى مجلد خاص مؤقت وتطابق نفس البايتات التي ستفك تشفيرها (لمنع استبداله بعد الفحص)، وتستفيد من فحوص S6 لسلامة القيد المحاسبي والملفات المشفرة. إذا نجحت، تستعيد قاعدة البيانات إلى **مجلد جديد فقط**، وتشغّل تطبيق FastAPI في عملية Python ثانية باختبار ASGI محلي على **نسخة عمل مؤقتة** بحيث لا يغير الاختبار بايتات القاعدة المستعادة.

تتحقق الأداة أن `/health` يعيد 200 وأن `/api/me` يرفض الزائر غير المسجل 401. تنتج `recovery_report.json` فيه حالات PASS وبصمات وأكواد HTTP فقط، بدون ملفات مستندات أو معلومات المرضى أو كلمات مرور أو مبالغ. الملفات المستعادة ذات وضع 0600 والمجلد الجديد 0700 على أنظمة POSIX. في حالة الفشل تحذف مجلد التجربة الذي أنشأته بنفسها فقط؛ لن تكتب فوق قاعدة موجودة أو تنقل تشغيل النظام تلقائيًا.

## تعليمات التطبيق الفعلي لمسؤول IT — على **جهاز آخر مشفر**

1. IT ومسؤول المالية يختاران نسخة احتياطية `.rbe` من وسيط معتمد، ويُسجلان وقت النسخ ووقت آخر حركة مالية مقبولة وRPO/RTO المطلوبين. **لا تستخدموا أرشيفات تحتوي على بيانات مرضى خارج البيئة المصرح بها**.
2. على جهاز المصدر، احصلوا على البصمة مستقلًا من ملف `.rbe` نفسه:
   - Linux: `sha256sum /secure/backups/ramses-YYYY.rbe`
   - macOS: `shasum -a 256 /secure/backups/ramses-YYYY.rbe`
   - Windows PowerShell: `Get-FileHash -Algorithm SHA256 C:\secure\backups\ramses-YYYY.rbe`
3. انسخوا **الأرشيف المشفر فقط** إلى قرص الجهاز البديل المشفر والمقيد بمسؤول IT، وانقلوا البصمة بطريق مستقل. حافظوا على مفتاح الاستعادة في خزنة أسرار/وسيط مختلف، ولا تضعوا المفتاح بجانب الأرشيف ولا في Git أو البريد أو الدردشة.
4. على الجهاز البديل، ثبّتوا نسخة السورس المعتمدة ومكتبات `requirements.txt` في بيئة Python مهيأة، ووفروا ملف كلمة مرور خاصًا بمستخدم الاستعادة وصلاحياته 0600 إن كان النظام POSIX، ثم شغّلوا:

```bash
export RAMSES_BACKUP_PASSPHRASE_FILE=/encrypted_private_key_store/backup-passphrase
python scripts/recovery_drill.py \
  --archive /encrypted_recovery/received-backup.rbe \
  --expected-sha256 REPLACE_WITH_SOURCE_DEVICE_64_CHARACTER_SHA256 \
  --output-dir /encrypted_recovery/NEW_AND_NONEXISTENT_DRILL_DIRECTORY
```

> في Windows استعملوا متغير البيئة `RAMSES_BACKUP_PASSPHRASE_FILE` بآلية PowerShell المأمونة، مع صلاحيات NTFS مقيدة. لا تستخدموا نفس القرص غير المشفر ولا كلمة مرور الاختبارات الموجودة في السورس.

5. احفظوا تقرير `recovery_report.json` في نظام تدقيق المؤسسة بعد المراجعة، وأكملوا **اختبارًا بشريًا فعليًا على جهاز مختلف**: تشغيل واجهة الشبكة المعتمدة، تسجيل الدخول بهوية اختبارية مصرّح بها، تقرير اليوم، قيود الأستاذ، استرجاع مستندات الإثباتات المخزنة داخل القاعدة، وحسابات الموردين/المرضى/الخزنة، مع مطابقة مستندات/وسائط خارج SQLite بطريقة مستقلة.
6. يجب أن يوقّع **IT والمالية والإدارة الطبية** على نجاح/فشل الفحص وملاحظات الشبكة والطابعات، وموعد آخر نسخة مالية يمكن استعادتها (RPO) والمدة المستغرقة (RTO). لا تنقلوا القاعدة المستعادة إلى التشغيل إلا بعد خطة رجوع وموافقة تشغيل منفصلة.

استخدموا [قالب محضر الاستعادة الفعلية](docs/project-autopilot/S7_PHYSICAL_RECOVERY_UAT_AR.md) لتسجيل الأدلة والتوقيعات. القالب غير موقّع ولا يثبت حدوث تجربة خارجية.

## معايير النجاح والفشل

- **PASS محلي تقنيًا:** بصمة النقل مطابقة، AES-GCM والمحتوى المالي سليمان، `recovered.sqlite3` جديد خاص، عملية FastAPI مستقلة نجحت، الضيف رُفض، ملف تقرير محجوب من البيانات الحساسة.
- **FAIL:** البصمة خطأ، كلمة المرور غير صحيحة، الأرشيف تالف أو SQL غير متوازن/إثبات تالف، المجلد موجود مسبقًا، التطبيق لا يعمل من نسخة الاستعادة. لا تُعدِّلوا الأرشيف كي ينجح.
- **لا يعني PASS:** تجربة على جهاز مستقل، نسخ خارج الموقع، مطابقة ملفات أصلية محفوظة خارجيًا، توقيع IT أو المراجع المالي، صلاحية فتح التشغيل الحقيقي، أو إثبات V8.0 التاريخي.
