# V8.1E-G2R — Project Autopilot M4 / bed occupancy and priced nightly orders (31 Oct 2026)

Development-only addition based on **G2Q**; neither installed in hospital nor approved for live patient/payment use.

- New `bed_stays.py` + `schema.sql` structures for inpatient/NICU beds, period-scoped occupancy and immutable nightly service snapshots.
- Owner creates beds and records administrative admission/release only with evidence; cashier/reviewer read solely their authorized patient cases. No clinical discharge approval is represented.
- Date-effective room tariffs reuse the existing service price table; preview shows calendar nights **[start_date,end_date)**. This is a **provisional proposed rule**, NOT approved hospital billing policy; accountant and medical operations must confirm nights, partial days, transfers, payer, exemptions and month-end allocations.
- The owner explicitly orders missing nights as **billing_case_lines in ordered state**. Separate service fulfillment and invoice issuance remain necessary; no cash or GL posted when recording a bed or selecting nights.
- Concurrency constraints and SQL triggers prevent double occupancy, duplicate nights, cross-case snapshot links, unauthorized mutation of night evidence and re-opening financial cases. Financial case clearance blocks open bed stays and unrecorded nights. Same-day zero-night cancellation can still undergo independent no-charge review without fake invoices.
- NICU added as an additive seeded department; existing department IDs and historical records untouched.
- New regression tests: `test_v82_g2r_bed_stays.py`, `test_v82_g2r_bed_stays_ui.py`, `test_v82_g2r_upgrade.py` with frozen G2Q original schema. Test evidence: `QA_G2R_TEST_RESULTS.tsv` in release.

Next work: clinical custody/fulfillment role, signed tariff/partial-day policy, shift/transfer boundaries and long-stay month end; operations/NICU consumables -> inventory/procurement/suppliers -> doctors' fees. Non-production release gate remains **NO-GO**.

### 1) الجهاز والمكان

- Business Mini PC: Core i5 حديث أو Ryzen 5 PRO، RAM 16GB قابلة للترقية إلى 32GB، SSD NVMe 512GB على الأقل، Ethernet سلكي.
- UPS للـMini PC **والراوتر/ONT**؛ ضبط BIOS على Power On after AC loss؛ إغلاق آمن عند انخفاض بطارية UPS.
- وضع الجهاز في مكان مغلق جيد التهوية داخل المستشفى، وعدم استخدامه للتصفح اليومي أو تثبيت تطبيقات شخصية.
- اختر Ubuntu Server LTS حديثًا ومجربًا على الجهاز، تحديثات أمان تلقائية، مستخدم إداري منفصل مع SSH keys، وتشفير القرص الكامل إن كان الاسترداد من انقطاع الكهرباء والتشغيل التلقائي متوافقين مع خطة التشغيل.
- نسخ احتياطي مشفر **خارج الجهاز وخارج المستشفى**. وجود نسخة على نفس قرص السيرفر وحده لا يحمي من السرقة أو تلف القرص أو الحريق.

### 2) تثبيت Docker على Ubuntu Server

اتبع دليل Docker الرسمي (لا تشغّل سكربت curl مجهول):
https://docs.docker.com/engine/install/ubuntu/
ثم تأكد من `docker compose version` و`docker version`.

احتفظ بمجلد النظام دائمًا في `/opt/ramses`، ولا تضعه ضمن مجلدات موقع عامة. بعد فك الحزمة:

```bash
sudo install -d -m 0750 -o "$USER" -g "$USER" /opt/ramses
# انقل ملفات مجلد ramses_accounts هنا بصفتك المستخدم الإداري؛ لا تنقل ZIP إلى مجلد عام
cd /opt/ramses
python3 scripts/setup_local.py
sudo chown -R 10001:10001 data backups secrets
sudo chmod 700 data backups secrets
sudo chmod 600 .env
sudo docker compose up -d --build
sudo docker compose ps
curl --fail http://127.0.0.1:8000/health
```

- سكربت `setup_local.py` يولّد كلمة مرور قوية للمالك **مرة واحدة** ويعرضها في الطرفية؛ احفظها في مدير كلمات مرور، ولا ترسلها لأحد أو في المحادثة.
- أول تسجيل دخول يتم **بعد نشر العنوان عبر HTTPS** لأن المتصفح يرفض كوكي Secure عبر HTTP.
- بعد التأكد من أول دخول، امسح سطر `RAMSES_ADMIN_PASSWORD` من `.env`؛ البيانات المعتمدة على المستخدم محفوظة بالفعل في قاعدة البيانات ولا تحتاج كلمة المرور الأولية لإعادة التشغيل. ثم `sudo docker compose up -d --force-recreate`.
- لا تغيّر ربط المنفذ `127.0.0.1:8000:8000` إلى `0.0.0.0`. لا تُفعّل Port Forwarding على الراوتر.

### 3) الوصول الخاص من أي مكان (Cloudflare)

1. أضف دومين تديره بحساب Cloudflare، أو استخدم دومين موجودًا بالفعل. الدومين نفسه قد تكون له تكلفة سنوية.
2. من Cloudflare Zero Trust **أنشئ تطبيق Access من نوع Self-hosted** *قبل* إنشاء مسار Tunnel، باسم مثل `accounts.example.com`، واجعل Allow مقتصرًا على بريدك وبريد كل موظف مصرح له فقط. لا تستعمل Allow Everyone أو Bypass.
3. فعّل تحقق الهوية القوي (MFA/IdP إن أمكن)، ومدة جلسة مناسبة مثل 8 ساعات.
4. من Cloudflare Networking > Tunnels أنشئ Tunnel مُدارًا من لوحة التحكم. ثبّت `cloudflared` على نظام الـMini PC كخدمة systemd باستخدام الأوامر الرسمية التي تظهر لك. **التوكن سري؛ لا يُنشر ولا يُرسل في الشات.**
5. أنشئ Public Hostname مطابقًا لتطبيق Access، والـ origin هو `http://127.0.0.1:8000`.
6. فعّل `Protect with Access` على إعدادات الـTunnel/hostname إن كان الخيار متاحًا؛ للتحقق من Access JWT عند الـorigin. لا توجّه Tunnel إلى أي منفذ إداري أو قاعدة بيانات.
7. تأكد من سلوك رفض الدخول ببريد غير مصرح، ثم اختبر دخول المالك وبعده مستخدم تجريبي من الموبايل على شبكة خارج المستشفى.
8. يتطلب Cloudflare Tunnel اتصالًا خارجيًا مستمرًا، وقد تحتاج السماح بخروج 7844 TCP/UDP من Firewall، دون فتح أي منفذ وارد.

مراجع رسمية:
- https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/self-hosted-public-app/
- https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/get-started/create-remote-tunnel/
- https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/configure-tunnels/tunnel-with-firewall/

**مهم:** عنوان HTTPS موجود على الإنترنت، لكن Cloudflare Access يُقفل وصول غير المصرح لهم قبل ظهور الموقع. حماية المستخدم/كلمة المرور داخل الموقع تبقى طبقة ثانية.

### 4) المزامنة مع Google Sheets (اختياري بعد فحص الموقع)

- شيت **التجارب فقط** `1BIjVrtYUlt8lOtaarZPyz4Cci0XIp5eWIJwOCfUfTTk`، ولا توجّه أي اختبارات إلى شيت الإدارة الأصلي.
- أنشئ Google Cloud Service Account له صلاحيات Sheets المطلوبة، وشارك **الشيت التجريبي فقط** مع بريد الخدمة، دون مشاركته مع الموظفين.
- ضع ملف JSON السري داخل `/opt/ramses/secrets/service-account.json` بصلاحيات وصول لحساب تشغيل الحاوية فقط (`chmod 600` و`chown 10001:10001`).


### 5) النسخ الاحتياطي واستعادة البيانات

**G2Q — النسخ الاعتيادي مشفّر فقط، ولا توجد نسخة SQLite مكشوفة بالطريق الافتراضي.** تحتاج إنشاء ملف كلمة مرور قوي (16 بايت على الأقل) على السيرفر داخل `secrets/backup_passphrase`، يملكه UID 10001 وبصلاحيات `0600`، مع صلاحية مناسبة لكتابة `backups/encrypted`. لا تكتب كلمة المرور في `.env` أو في أوامر التشغيل أو في مستودع Git.

```bash
# بعد إعداد كلمة المرور محليًا خارج مصدر المشروع
sudo /bin/sh scripts/backup_local.sh
# تنشئ الحاوية ملف .rbe مشفرًا وتتحقق من سلامته قبل نشره في backups/encrypted
# تحقق مستقل مع نفس مفتاح النسخ:
# RAMSES_BACKUP_PASSPHRASE_FILE=/path/to/owner-only-secret python3 scripts/secure_backup.py verify --input /path/to/backup.rbe
```

ملف `backup.py` القديم أصبح واجهة توافق للنسخ المشفر نفسه، وفشل إعداد كلمة المرور **يوقف النسخ دون إنتاج ملف نصي غير مشفر**. إذا كانت لديك نسخ SQLite غير مشفرة من الإصدارات السابقة، عالجها بإجراءات احتفاظ وأمن مناسبة ولا ترفعها أو ترسلها عبر الإنترنت.

**مهم:** التشفير لا ينقل الملفات خارج الخادم تلقائيًا. انسخ ملفات `.rbe` إلى مخزن مستقل محمي ذي صلاحيات محدودة، واختبر استعادةً دورية على جهاز آخر، مع جرد للمرفقات وسجل توقيت النجاح/الفشل. `backups/` المحلي لا يكفي للتعافي من فقد الجهاز.

لنسخ محلي يومي الساعة 03:10 *بتوقيت نظام السيرفر*:

```bash
sudo cp systemd/ramses-backup.service systemd/ramses-backup.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now ramses-backup.timer
systemctl list-timers ramses-backup.timer
```

تأكد من ضبط المنطقة الزمنية `timedatectl set-timezone Africa/Cairo` على السيرفر بعد مراجعة إعدادات النظام.

### 6) التحديثات بدون GitHub Actions

في وقت صيانة وبوجود نسخة احتياطية **مُتحقق منها**: انسخ ملفات التطبيق الجديدة إلى `/opt/ramses` مع الاحتفاظ بالمجلدات `data/`, `secrets/`, `backups/`, `.env`. بعد مراجعة التغييرات شغّل:

```bash
sudo docker compose up -d --build
sudo docker compose ps
curl --fail http://127.0.0.1:8000/health
```

هذه الطريقة لا تحتاج GitHub أو Render. تحديث Docker Image ليس بديلاً عن تحديث Ubuntu وتثبيت ترقيعات الأمان.

### 7) قبول التشغيل الحقيقي

- إنشاء مستخدم مدير ومراجع ومدخل، وتأكيد أن لا أحد يعتمد سندًا أنشأه بنفسه.
- اختبار سند إيراد وصرف وتحويل وراتب تجريبي، وعكس سند واعتماد حركة، والتأكد من عدم تكرار إرسال السند.
- اختبار انقطاع الإنترنت وإعادة تشغيل الجهاز والـUPS والعودة التلقائية للخدمات.
- اختبار Backup + Restore **على قاعدة تجريبية منفصلة**، وليس فوق قاعدة المستشفى.
- مطابقة الأرصدة الافتتاحية الحقيقية بخزنة المستشفى والمحافظ والبنك قبل الإدخال؛ أرشيف يونيو السابق ليس رصيدًا افتتاحيًا معتمدًا.
- حماية القرص والوصول المادي ومراجعة حسابات Cloudflare دوريًا، وعدم تخزين معلومات المرضى داخل وصف السند إلا عند الحاجة والالتزام بسياسة بيانات مناسبة.
