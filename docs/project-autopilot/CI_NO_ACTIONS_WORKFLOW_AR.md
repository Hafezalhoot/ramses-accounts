# حسابات رمسيس — نظام اختبار بدون GitHub Actions أو استهلاك دقائقها

**قرار المشروع 5 نوفمبر 2026:** لا نفعّل GitHub Actions على هذا المستودع الخاص؛ اختبارات التطوير تعمل يدويًا في بيئة ChatGPT Work المتصلة بالمستودع أو على جهاز تطوير يملك Python وGit وNode. هذا القرار يضمن **عدم استهلاك دقائق GitHub-hosted Actions** بسبب عملنا هنا. قد تظل موارد Work أو جهازك خاضعة لحدودها الخاصة.

## الهيكل

- **GitHub خاص**: المصدر، التاريخ الكامل، الفروع وPull Requests فقط.
- **منفذ اختبارات خارج GitHub**: Work أو جهاز موثوق. لا نستخدم GitHub Actions، ولا نحتاج GitHub token داخل المشروع.
- **بوابة ثابتة داخل السورس**: `scripts/run_local_qa.py` تستنسخ نفس الـCommit في Git worktree مؤقتة، وتتحقق من سلامة Git وصياغة Python وJavaScript، ثم تشغّل `scripts/ci_smoke.py`. عند `--full` تشغّل كذلك `scripts/qa_g2t_full.py` مع `scripts/ci_audit_gate.py`، وتضع التقارير خارج المستودع.
- **الأدلة**: `run.json` يحفظ SHA ونتيجة كل خطوة؛ `audit.md` و`QA_G2T_TEST_RESULTS.tsv` والـlogs تفصل PASS عن SKIP وBLOCKED. لا تدّعي الشهادة التشغيلية.

## طريقة التشغيل في Work أو جهازك

1. استخدم نسخة Git كاملة (full history) من `Hafezalhoot/ramses-accounts`، وافتح الفرع/الـCommit المحدد للمراجعة. لا تعتمد على ZIP قديم بدل الفرع الجاري.
2. ثبت Python 3.13 وNode.js وGit. أنشئ بيئة Python افتراضية **خارج مجلد Git أو داخل مجلد متجاهَل**، ثم ثبت الاعتماديات من `requirements.txt`.
3. تأكد أن `git status --porcelain` فارغ وأن النسخة غير Shallow (`git rev-parse --is-shallow-repository` ترجع `false`).
4. من جذر المشروع شغّل:

```bash
python scripts/run_local_qa.py --full
```

فحص سريع فقط:

```bash
python scripts/run_local_qa.py
```

إذا كان لديك أرشيف السورس الأصلي V8.0 الذي تم فحصه، مرره صراحة (ليس قاعدة مستشفى):

```bash
python scripts/run_local_qa.py --full --v80-archive /ABSOLUTE/PATH/TO/Ramses_Accounts_V8_0_Double_Entry_Decision_Foundation.zip
```

الأوامر لا تُجري `pip install` تلقائيًا ولا تتصل بقواعد التشغيل. ضع `RAMSES_DB_PATH` أو أي متغير مرايا Google الحقيقية جانبًا قبل الاختبار؛ المشغّل يرفض البدء إن كانت مفعّلة.

## قواعد الأمان والمصداقية

- لا تشغيل على قاعدة مستشفى، ولا `.env` حقيقي، ولا بيانات مرضى أو موظفين في تقارير PR.
- **اختبار QA كامل موثوق فنيًا فقط** عندما ينتهي المشغّل بالرمز 0 وتُحفظ نتائج كل خطوة مرتبطة بــSHA؛ الترحيلات التاريخية التي تحتاج أرشيف/نسخة مفقودة تبقى SKIP أو BLOCKED بمسمّاها.
- مَن يراجع PR يقارن الـSHA في `run.json` بــHEAD الخاص بالفرع وبالـdiff، ثم يراجع التقرير والاختبارات؛ لا تدمج تغييرًا ماليًا لم تُختبر نسخته بالضبط.
- لا يوجد الآن **Required GitHub Status Check آلي**. الانضباط قائم على مراجعة بشرية وملف أدلة، ويمكن استخدام حماية الفرع باشتراط PR ومراجعات بشرية حيث تتوفر، من دون Actions. لا نعرض الاختبارات اليدوية كأنها فحص GitHub ناجح.
- لو تعرضت بيئة التطوير لفشل DNS في الوصول إلى GitHub، استخدم Work المتصل أو جهازًا لديه وصول، وليس كسر TLS أو نشر توكن في السورس. GitHub connector في المحادثة يدعم تعديل الملفات ومراجعتها لكنه لا يشغّل مشروع FastAPI كاملًا بنفسه.
- خدمة Work قد يكون لها حدود استخدام منفصلة؛ عبارة **No GitHub Actions minutes** لا تعني عدم وجود أي تكلفة حوسبة أخرى.

## ملحوظة الاستمرار

الـPR الخاص بالبنية الاختبارية يجب أن يبقى مسودة إلى أن تُنفذ تجربة على السورس الكامل مع Python 3.13 داخل بيئة مستقلة؛ اختبارات المشغّل المعزولة لا تثبت نجاح 160+ اختبار للمستشفى. وبعد مراجعة/دمج هذه البنية على `main`، انقل تغييرات S15 المالية إلى فرع محدث واختبرها بالأمر نفسه.

**الحكم النهائي حتى اعتماد البيئة: TEST ONLY / PRODUCTION NO-GO.**
