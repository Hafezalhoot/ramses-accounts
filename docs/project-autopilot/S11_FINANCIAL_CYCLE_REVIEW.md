## Verified findings

### F1 — P1: last bed night cannot be invoiced after month boundary; prior month cannot close

**Evidence:** `bed_stays.py:54–73,200–219`; `billing.py:735–746,982–988`; `bed_stays.py:323–331`.

A night dated the last day of a month cannot be created before the next day: the night loop uses `day < end`, and `through_date` cannot be future. The next day belongs to the next month, but ordinary draft creation only selects the current service month. Issuance also forbids any other service month, while the bed close gate requires an invoice and posted GL **inside the original service month**. There is no ordinary route that can satisfy these conditions.

**Synthetic probe:** process-only billing/bed clocks set to 2026-12-01; create normal operation/inpatient case and a bed stay starting 2026-11-30; keep November open; charge through Dec1 and independently fulfill. One 10000-piaster Nov30 night is created and fulfilled. POST ordinary draft returns HTTP409, `لا توجد خدمات منفذة غير مضافة لمسودة سابقة`. `month_close_bed_issue('2026-11')` returns `{kind: 'not_invoiced', night_date: '2026-11-30'}`. No real data or production clocks changed. Existing G2U test avoids day1 rather than testing last-night completion; G2S only proves close blocks, not that it can be resolved.

**Impact:** routine inpatient month-end billing and prior-month close are impossible once the last night completes. Ordinary services fulfilled before month end but invoiced after midnight face the same current-month selection restriction.

**Resolution boundary:** distinguish service period, issue date and posting date explicitly; add day1/last-night/old-open-vs-closed-period regression. The accountant must approve recognition and controlled late posting semantics. Do not silently backdate journals or reopen closed periods. This finding is real but its financial-date design is not chosen by this reviewer.

### F2 — P1: financial case close strands a pending consumables issue and blocks month close

**Evidence before fix:** `case_settlement.py:37–139` counts pending inventory returns but never pending `inventory_issues`; `inventory.py:1450–1455` rejects both approval and rejection for a closed case; `inventory.py:1885–1886` blocks month close while any issue remains pending. SQL `inv_return_case_close_pending_guard` protects returns only, not this API closure route.

**Synthetic probe:** create a no-charge operation case and a case-linked pending consumables issue through normal APIs. Preflight returns `no_charge_ready: true`; independent no-charge financial closure returns HTTP200. Attempt by independent inventory reviewer to reject the unused issue then returns HTTP409 `ملف الحالة أُغلق أثناء انتظار اعتماد الصرف`; issue stays `pending`; inventory month-close gate reports `أذون صرف مستلزمات تنتظر اعتماد مراجع مستقل`.

**Impact:** an ordinary booking cancellation can create an unrecoverable pending inventory document and prevent monthly closure. The settled-case approval path also reuses the same preflight and omits this pending-source check.

**Narrow authorized fix:** include pending case-linked inventory issues in clearance preflight, block both settled and no-charge readiness, and recheck at independent clearance approval under the existing IMMEDIATE transaction. Keep inventory approval/rejection rules, source records, cash and GL unchanged. Coordinator authorized this policy-free fix after reproduction. Implemented in `case_settlement.py` only: count pending case-linked issues, include them in both readiness modes and return the count/blocker. Existing request and independent-approval transactions reuse this preflight. `tests/test_s11_case_inventory_pending.py` failed first on the demonstrated no-charge readiness defect, then passed after the minimal fix. Logs: `docs/project-autopilot/evidence/S11/case-inventory-red.log`, `case-inventory-green.log`, `case-inventory-regression.log`. Existing G2P case settlement, G3C case consumables cost and G3D inventory returns regressions also passed. Full suite remains parent-owned. Older stranded cases need an independently approved recovery path; this patch does not reopen them or relax inventory rejection/approval semantics.
