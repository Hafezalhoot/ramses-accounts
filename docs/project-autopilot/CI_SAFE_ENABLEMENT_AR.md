# استعادة CI مستقلة وآمنة لمشروع حسابات رمسيس — 5 نوفمبر 2026

**الحالة:** تنفيذ Workflow على فرع مراجعة فقط، ولا يعتبر CI مفعلًا أو ناجحًا حتى يظهر تشغيل فعلي على GitHub. **TEST ONLY / PRODUCTION NO-GO**.

## تشخيص جذور المشكلة

1. مستودع `Hafezalhoot/ramses-accounts` **Private** ومتصل للقراءة/الكتابة عبر GitHub، لكن حاوية تنفيذ هذه المحادثة لا تحل اسم `github.com` (`getent hosts` فشل و`curl` خرج برمز 6). الاتصال بالمستودع عبر الـConnector لا يحول الحاوية إلى Runner متصل بالإنترنت.
2. GitHub Actions تعطّل عمدًا قبل رفع تاريخ المستودع، وسُحب workflow من `.github/workflows/` في `main`. لا يوجد تشغيل Actions سابق مسجل عند المراجعة. هذا إعداد إداري منفصل عن ملفات المشروع، ولا تتيحه أدوات GitHub المتصلة للكتابة هنا.
3. Workflows قديمة ما زالت في بعض الفروع التاريخية `development/s13`, `development/s14`, `stabilization/s10`، وتستخدم `on: push` بلا قيد. **تجنب الدفع إلى هذه الفروع بعد إعادة التفعيل**؛ احتفظ بالتاريخ ولا تستخدم force-push.
4. ملف Workflow القديم استخدم Python 3.12 وعمل `checkout` سطحيا، في حين أن أحدث المصدر يتطلب Python 3.13 وبعض اختبارات الترحيل تحتاج `git show` لنسخ سابقة، لذلك يجب `fetch-depth: 0`.
5. `qa_g2t_full.py` سابقًا اعتبر `BLOCKED_NO_V80` حالة غير فاشلة في كود الخروج؛ وهذا لا يعني نجاح اختبار الترحيل. لذلك أضيفت بوابة مستقلة توضح النقص وتمنع تجاوزات جديدة غير معروفة.

## ماذا يحقق Workflow الجديد

- تشغيل تلقائي على Pull Requests إلى `main` وبعد الدمج إليه؛ ويمكن استدعاؤه يدويًا بـ`workflow_dispatch`.
- وظيفتان منفصلتان: **Finance smoke (Python 3.13)** و**Full synthetic regression (fixture-aware)**.
- تشغيل على `ubuntu-24.04` مع Python 3.13 وGit كامل. جميع Actions الخارجية الثلاث مثبتة بـSHA من مستودعات GitHub الرسمية (`checkout`, `setup-python`, `upload-artifact`).
- `GITHUB_TOKEN` بصلاحية `contents: read` فقط، و`persist-credentials: false`، ولا `secrets`, ولا `pull_request_target`, ولا وصول لبيانات المستشفى أو نشر تلقائي.
- مراجعة ملفات Git المحظورة قبل smoke: `.env` الفعلي و`private/` وقواعد `.sqlite/.db` والنسخ المشفرة وحزم الترحيل.
- فحص صياغة Python/JS و`pip check`، والاختبارات المالية المصدرية، ثم المجموعة الشاملة في عملية مستقلة.
- تحليل TSV بوحدة `scripts/ci_audit_gate.py`: حد أدنى 160 اختبارًا (159 سابقًا + اختبار البوابة)، مع اختبار أتعاب S14 ضمن الملفات الإلزامية، ومنع أي `FAIL/TIMEOUT` أو تجاوز غير معتمد، ورفض التقرير المفقود/المكرر.
- يسمح **فقط** للخمسة `SKIP` التاريخية المعروفة وحالة `BLOCKED_NO_V80` المعروفة كاستثناءات مثبتة من **بوابة انحدار المصدر**؛ يعرضها صراحة في ملخص GitHub. هذا ليس نجاحًا لجميع الاختبارات ولا شهادة جاهزية إنتاج.
- يخزن ملخصًا خاليًا من سجلات المرضى/الاعتمادات كـArtifact خاص بالمستودع لمدة 7 أيام؛ لا يرفع قواعد أو نسخًا احتياطية.
- يوقف تشغيلات نفس PR الأقدم لتقليل استهلاك دقائق CI.

## الإجراء الإداري المطلوب مرة واحدة من مالك المستودع

بما أن اتصال GitHub في هذه المحادثة لا يعرض API لتغيير **إعدادات GitHub Actions للمستودع**، فلا يمكن ادعاء إعادة تفعيلها تلقائيًا. بعد مراجعة PR الخاص بالبنية:

1. افتح **GitHub → Hafezalhoot/ramses-accounts → Settings → Actions → General**.
2. ضمن **Actions permissions** اختر السماح بتشغيل **Actions created by GitHub** (على الأقل `actions/checkout`, `actions/setup-python`, `actions/upload-artifact`) أو سياسة تضبط تلك الثلاثة تحديدًا. **لا تمنح صلاحيات لكل Action خارجي عشوائيًا**.
3. ضمن **Workflow permissions** اختر **Read repository contents permission**، ولا تفعّل قدرة Actions على إنشاء/اعتماد PRs. لا تُدخل أسرارًا ولا بيانات مستشفى في GitHub Actions.
4. احفظ الإعداد. إن كان على مستوى الحساب أو المؤسسة منع أعلى، راجعه مع مالك الحساب؛ GitHub قد يحجب Actions بقرار من المنصة نفسها.
5. اطلب إعادة تشغيل/تحريك PR البنية بعد التفعيل. لا تعتمد مجرد ظهور الملف: يجب رصد تشغيل جديد للوظيفتين بنتيجة فعلية مع السجلات.
6. بعد نجاح فحوص PR للبنية ومراجعتها، ادمجه بشكل عادي في `main` (بلا force-push)، وأعد مزامنة فرع S15 مع أحدث `main`، ثم شغّل فحوصه تلقائيًا.
7. بعد ظهور أسماء الوظائف الفعلية في GitHub **Settings → Branches / Rulesets**، اجعل **Finance smoke (Python 3.13)** و**Full synthetic regression (fixture-aware)** فحوصًا إلزامية قبل دمج `main`، مع PR ومراجعة مستقلة للتغييرات المالية. لا ترفع هذا القيد إلا بقرار واضح.

> قد يحتسب GitHub دقائق تشغيل أو رسومًا للمستودع الخاص حسب خطة الحساب والاستهلاك. لا توجد تشغيلات دورية في الإعداد الحالي؛ فقط PR وPush إلى `main` والتشغيل اليدوي.

## التشغيل البديل عندما لا تعمل GitHub Actions بعد

داخل بيئة Work/Codex **مصرح لها باستنساخ المستودع الخاص**، على فرع حديث بقاعدة اختبار صناعية، بعد تثبيت Python 3.13:

```bash
python3.13 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m pip check
.venv/bin/python scripts/ci_smoke.py
.venv/bin/python scripts/qa_g2t_full.py
.venv/bin/python scripts/ci_audit_gate.py QA_G2T_TEST_RESULTS.tsv
```

الأرشيف الأصلي V8.0، إذا كان متاحًا لجهاز Work المؤمَّن، يدخل كـFixture منفصل عبر `RAMSES_V80_ARCHIVE` للاختبار؛ لا يُرفع إلى مستودع المصدر ولا إلى GitHub Secrets دون تصميم تخزين وخصوصية صريح. نتائج الخمسة SKIP والـBLOCKED يجب أن تظل معلنة. الاختبارات على Runner صناعي ليست استعادة جهاز مستقل أو UAT ولا اعتماد Finance/Medical/IT.
